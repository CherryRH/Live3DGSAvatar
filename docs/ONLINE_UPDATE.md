# 在线更新（热更新）

> 通话开始时，用一小段摄像头观测**微调已有模型的外观**，让它在当前光照/相机/姿态下更准。
> 目标耗时 ~10 秒（本机 GPU 较弱时可放宽）。

## 0. 它是什么方法（不是什么）

**逐高斯自由参数的直接优化（test-time optimization / analysis-by-synthesis）**，
不是训练神经网络。

| | 现状 |
|---|---|
| 优化变量 | `color_delta [N,1,3]`（+ 可选 `opacity_delta [N,1]`）—— 每个高斯一份，**自由参数** |
| 优化器 | Adam（`lr_color=2e-3`，`lr_opacity=2e-2`） |
| 损失 | 渲染图与 `images/` 的掩码 MSE（可选 L1） |
| 梯度从哪来 | **可微光栅化器**（differentiable rendering） |
| 神经网络 | **不训练**。`weight_module`（MLP）与约简 blendshape 全部**冻结**，只用来把 129 维参数变成基础高斯 |
| 参数量 | 60353 × 3 ≈ 18 万（颜色），与"训练"一个网络无关 |

换个说法：给定**一个场景 + 一小段观测**，解一个"让渲染匹配观测"的逆问题。
它天然只会拟合观测到的东西 —— 这就是为什么泛化到未见帧很弱（见 §5b）。

`--dry-run` 里的闭式颜色校正是**最小二乘**（解一个 3×3 矩阵 + 偏置），
更不涉及网络。

要真正提升泛化，需要的是**学习先验**（回归器：观测 → 修正量），
那是另一个训练任务，见 §7。

## 1. 它修什么，不修什么

| 能修 | 不能修 |
|---|---|
| 全局色调 / 白平衡 / 曝光偏差 | **未观测区域**（如被裁掉的头顶） |
| 逐高斯的颜色与不透明度误差 | 几何/姿态误差 |
| 当前光照下的观感差异 | 驱动参数（表情基）的误差 |

**边界是刻意的**：热更新解决"外观偏差"，不是"重建更好的模型"。
未观测区域在**任何**优化里都没有梯度 —— 那要靠补拍或对称先验解决。

### 实测依据

`crh_1` 的模型里，暗高斯（亮度 < 0.2）有 10693 个，其中：

- **82%** 落在图像同位置**也暗**的区域 → 是头发，不是缺陷
- **7%** 落在图像**亮**的区域 → 真正的模型缺失（约 700 个高斯）

所以"头顶缺失"**大部分是错觉**，能修的只有一小部分。

## 2. 为什么只更新「颜色 + 不透明度」

| 参数 | 是否更新 | 原因 |
|---|---|---|
| `color`（SH DC） | ✅ | 外观偏差的主要载体 |
| `opacity`（logit） | ✅（可关） | 修正"该透明处不透明"这类误差 |
| `xyz` / `rotation` / `scaling` | ❌ | 几何一动，绑定关系与多帧一致性都会变 |
| 融合基 `*_b` | ❌ | 是训练学到的表达空间，小数据量下改它只会破坏 |
| `weight_module`（MLP） | ❌ | 10 s 内迭代量不足以学新映射 |

参数规模：**6 万 × 3（颜色）+ 6 万（不透明度）**，而不是 600 万全参数。

## 3. 三个组件

```
training/
├── observations.py   观测契约（帧 + 相机），与来源无关
├── losses.py         掩码 MSE / PSNR（优化目标与验收判据同源）
├── color_fit.py      闭式颜色校正（9~12 参数，零迭代）
└── updater.py        梯度微调（颜色/不透明度，带墙钟预算）
```

### 3.1 观测契约（解耦的关键）

```python
FrameObservation(mesh=..., blend_weight=..., target=..., mask=..., name=...)
BatchObservation(frames=[...], camera=...)
```

`training/` **不 import `data/` 或 `app/`**（有测试守护）。因此：

| 来源 | 谁负责构造 `FrameObservation` |
|---|---|
| 数据集 | `data/scene.py` + 读图 |
| 摄像头 | 以后接 RDF 的那一侧 |

**同一条更新逻辑，两种来源**。加摄像头时不需要改 `training/`。

### 3.2 闭式颜色校正（先做这个）

拟合 `rgb' = rgb @ M + b`，`M` 为 3×3、`b` 为 3 维 —— **12 个参数，最小二乘一步解完**。

```python
corr, metrics = fit_color_correction(predicted, target, mask)
print(metrics["psnr_delta"])     # 拟合前后差多少 dB
```

实测（`crh_1`，逐高斯点对点）：**+1.3 dB**，且跨帧可迁移。
它**作用于渲染输出**，不修改 `model.ply`，可与梯度微调叠加。

### 3.3 梯度微调

```python
updater = OnlineUpdater(avatar, rasterizer, UpdateConfig(steps=300, time_budget_s=10))
report, state = updater.fit(batch, background=bg)
print(report.summary())      # PSNR before → after
```

- 增量存在 `UpdateState` 里（**不改模型参数**）→ 可回滚、可只保存增量
- `time_budget_s` 是硬约束：到点即停，保证通话不被卡住
- 支持流式：`fit(state=上一轮)` 从已有增量继续

## 4. 验收判据与实测结果

**PSNR（掩码内）**，与渲染测试一致。

### 实测（`crh_1`，8 帧，512²，RTX 3090）

```bash
CUDA_LAUNCH_BLOCKING=1 python scripts/online_update.py --frames 8 --time-budget 10
```

```
热更新 182 步 / 10.24s：PSNR 31.37 → 32.52 dB (+1.15)
  过程: @50:32.55, @100:32.60, @150:32.56
```

**收敛很快**：第 50 步就到 32.55，之后 132 步只再涨 0.05 dB 且略有回落。
即 **~3 秒能拿到几乎全部收益**，10 秒预算对质量没有额外贡献。

单步约 56 ms（8 帧 × ~7 ms 前向+反向）。

> ⚠️ `elapsed_s` 包含收尾的 `after` 评估，所以它略高于纯迭代耗时。
> `--time-budget` 在**每步开始前**检查，因此实际耗时最多超出一个 step + 一次 eval。

### 与渲染测试基线的关系

| 数值 | 口径 |
|---|---|
| 30.71 dB | 20 帧，PSNR 的**中位数**（`render_test`） |
| 31.37 dB | 8 帧，PSNR 的**均值**（`online_update` 的 before） |

两者**统计口径不同**，不可直接比较；热更新的验收看**同一批帧上的前后差值**。

⚠️ 注意基线是**训练数据上**的结果；摄像头链路的基线会更低（光照/跟踪精度差异），
**不能用上述数值当起点**。

## 5. 使用

```bash
# 只测闭式颜色校正（不需要 GPU）
python scripts/online_update.py --dry-run

# 完整热更新（需要 GPU）
python scripts/online_update.py --frames 8 --time-budget 10

# 跨对象：用 crh_2 的画面更新 crh_1 的模型，并输出对比图
python scripts/online_update.py \
    --subject crh_1 --data-subject crh_2 \
    --frames 300 --time-budget 10 \
    --compare-frames 8
```

### 跨对象（模型 A ← 数据 B）

`--subject` 是**模型**、`--data-subject` 是**观测/驱动数据**，两者独立。
不给 `--data-subject` 时与原行为一致（同一对象）。

> ⚠️ 在线更新只改**颜色与不透明度**，改不了身份/形状。
> 用 crh_2 的画面驱动 crh_1 的模型时，PSNR 的**绝对值**受身份差异限制，
> 有意义的是**前后差值**。脚本会在开头打印这条提示。

### 为什么不需要 RDF

观测直接来自数据集的 `render_inputs.npz`：逐帧的**网格顶点**与 **129 维驱动参数**
是预处理阶段（训练管线用 RDF 离线跑出来的）就存好的。在线更新只消费这两个量，
不做任何 3DMM 前向，所以不需要 RDF、不需要 GPU 推理追踪器。

RDF 只在**实时摄像头**输入时才需要（见 `LIVE_DRIVING.md`）。

### 到底在"更新"什么

| | 目标从哪里来 | 优化什么 |
|---|---|---|
| 训练/在线更新 | `images/`（已抠图的 RGBA，黑底）| 逐高斯的 **SH DC 颜色** 与 **不透明度 logit** |
| 对比图三格 | 同上：`images/` + 两次渲染 | — |

`input/`（视频裁出的原图，白墙背景）**不参与任何计算**：背景不同会让观感对比失真，
把背景差异误读成"模型变差"。三格统一用抠图目标后，PSNR 也正好是在同一批像素上算的。

**颜色不是"直接采样 input 的颜色"**。流程是：

```
129 维参数 → MLP → 约简 blendshape → 每高斯颜色偏移 → 光栅化 → 与 images/ 比像素
                                    ↑
                    优化的是这里：一个 [N,1,3] 的 per-Gaussian 增量
```

即：**渲染出图后再与抠图目标逐像素比**，梯度回传到每个高斯的颜色/不透明度。
不是把 2D 像素投到高斯上，也没有"取输入图颜色"这一步。

⚠️ 不透明度是 **logit**，库里 5.4% 的高斯 logit = -9999（占位、不可见）。
`lr_opacity=0.02` 在几十步里能让有效高斯的透明度变化 0.1–0.2 ——
**PSNR 可能因此变好（透出黑底去贴合暗部），但画面会发虚/发暗**。
判断方法：脚本现在会打印 `[增量规模]`，若"变化超过 0.2 的高斯"很多，
试 `--no-opacity` 对比。

### 涂色实验（能力测试，不是泛化实验）

把目标画面的指定区域涂成纯色，看更新能否把**渲染**也刷成该色。
这是检查"更新机制本身通不通"的最小实验：

```bash
# 左半边涂绿
python scripts/online_update.py --subject crh_1 --data-subject crh_2 \
    --frames 60 --no-opacity --paint left --paint-color 0,255,0 --compare-frames 4

# 绿色竖条（更细的空间频率，测容量）
python scripts/online_update.py ... --paint stripes --paint-param 16
```

图案：`left` / `right` / `stripes` / `checker`（`--paint-param` 是格子边长）。

**关键设计：只改 RGB，不动 alpha。**
alpha 决定"哪些像素参与损失"；若把涂色区（含背景）也纳入损失，
模型永远渲染不到背景，会留下一个降不下去的残差 —— 实验结论会被误导。

脚本会给出**三组指标**，各回答不同问题 —— 不要混着看：

```
[涂色实验] 三组指标
  ① 被涂区域 vs 涂色值：色差 128.4 → 18.7 /255（-109.7）
     接近目标色(±40)的像素 2.1% → 91.3%    ← 这一项才说明"学会了没有"
  ② 未涂区域 vs **原图**：PSNR 26.31 → 25.87 dB（-0.44）  ← 附带损伤
  ③ 整体 vs 涂色目标（PSNR 表）只有 8–9 dB 是**正常的**
```

| 指标 | 回答什么 | 什么时候看 |
|---|---|---|
| ① 涂色区色差/接近率 | 更新机制能不能把颜色推到目标 | 判断"机制通不通" |
| ② 未涂区 vs 原图 | 没让改的地方被改坏多少 | 判断"自由度有没有互相牵连" |
| ③ 整体 vs 涂色目标 | 渲染与"半绿半真"的目标有多像 | **没有诊断价值**，别用它判断好坏 |

⚠️ **不要把主指标换成"vs 原图"**：涂色实验的优化目标就是涂色后的图，
对原图算 PSNR 与优化目标无关 —— 它衡量的是"更新把模型拉离原本外观多远"，
不是"更新有没有生效"。两个问题必须分开报。

若 ① 的"接近率"几乎不涨、色差仍很大，说明**问题在更新机制/学习率**，
而不是泛化 —— 这是这个实验最有价值的用途：把两类问题分开。

### 输出目录：按**实验名**分层

```
output/online_update/
└── crh_1__from-crh_2__f300__noop__L2__all/
    ├── 00000.png … 003523.png     # 对比图（每张 3 格）
    ├── state.npz                  # 更新增量（<1 MB）
    └── metrics.json               # PSNR 前后、步数、耗时、过程
```

实验名由关键参数生成（`<模型>[__from-<数据>]__f<帧数>__<op|noop>__<L1|L2>__<all|cmp N>`）：

| 参数 | 例子 |
|---|---|
| `--subject crh_1 --data-subject crh_2` | `crh_1__from-crh_2` |
| `--frames 300` | `__f300` |
| `--no-opacity` | `__noop` |
| 损失 | `__L2` / `__L1` |
| `--compare-frames -1` | `__all` |

**同参数重跑覆盖同一目录**（便于比较，不堆垃圾）；参数一变目录就变
（不同实验不会混在一起）。也可用 `--exp-name` 显式指定。

### 显存：为什么 `--compare-frames -1` 曾经 OOM

| 组成 | 每帧 | 3524 帧 |
|---|---|---|
| 目标图 `[3,512,512]` float32 | **3.00 MB** | **10.3 GB** |
| 掩码 `[512,512]` bool | 0.25 MB | 0.86 GB |
| 网格 `[5083,3]` float32 | 61 KB | 0.20 GB |
| 更新增量（全局一份） | — | <1 MB |

**元凶是目标图**，不是模型、也不是增量。所以现在的策略是：

- **mesh 全留**（3524 帧才 0.2 GB）
- **拟合集的目标图驻留**（默认 300 帧 ≈ 900 MB）
- **对比图逐帧读、用完即弃**（峰值只多一帧）

拟合集超过约 1.5 GB 会打印警告。真要大 `--frames` 时，可以分多次不同帧段跑
并在后续版本里做流式加载。

### 对比图

`--compare-frames N`：**从第 0 帧开始连续取 N 帧**（不是等距抽样）；
`-1` = 全部数据集帧。每张**一排三格**：

```
┌────────────────┬────────────────┬────────────────┐
│ target 00042   │ before 24.1 dB │ after 26.3 dB  │
├────────────────┼────────────────┼────────────────┤
│ crh_2 抠图目标  │ 更新前拟合      │ 更新后拟合      │
└────────────────┴────────────────┴────────────────┘
```

| 参数 | 含义 |
|---|---|
| `--frames M` | **用于更新**的观测帧数（现实里几十帧通常就够）|
| `--sample` | 观测帧怎么选：`uniform`（默认，全片等距）/ `random` / `head` |
| `--seed` | `--sample random` 的种子（可复现）|
| `--compare-frames N` | **对比多少帧**，从第 0 帧起连续取；`-1` = 全部 |
| `--compare-dir` | 输出目录；默认 `<output_dir>/online_update/` |

两者**互相独立**：可以用 60 帧更新、输出全部对比图。

### 观测帧为什么默认均匀采样

连续几秒的片段里姿态与光照几乎不变，在它上面拟合出的颜色偏移等于只拟合那一小段。
实测（`--frames 300 --sample head`）：参与拟合的前 300 帧 **+0.73~0.85 dB**，
未参与的帧只有 **+0.05 dB**（中位 +0.08，378 帧变差）。

均匀采样把同样的帧数摊到整段视频上，代表性更好。想复现旧行为用 `--sample head`。

### 每步用不同的帧（mini-batch）

`frame_chunk` 是**每步**用几帧。原实现是 `batch.frames[:frame_chunk]` ——
等于每步都用同一批：300 帧观测 + `frame_chunk=8` 时，**只有前 8 帧产生过梯度**，
另外 292 帧只在评估里出现。现在按步轮转（可复现，且每 `ceil(N/k)` 步覆盖全部帧）。

**N > M 时多出来的帧没有参与拟合** —— 那正是看**泛化能力**的部分
（`--compare-frames -1` 会对比全部 3524 帧，其中 3224 帧是held-out）。
表格里会给这些帧标 `(未参与拟合)`。

**三格同背景、同口径**：都是 `images/`（黑底、抠图），PSNR 就按 `images/` 的
alpha 掩码在同一批像素上算。不需要额外处理背景。

配置见 `configs/train.yaml` 的 `train.online_update` 节；GUI 设置面板也能改
（「训练 / 在线更新」分组）。

### 门控

| 门控 | 关闭时的行为 |
|---|---|
| `enabled` | 脚本打印 `[skip]` 并退出（加 `--force` 可强制跑一次）；GUI 不触发更新 |
| `update_color` | 颜色不进优化器（`color_delta` 保持为零） |
| `update_opacity` | 不透明度不进优化器 |
| `color_l1` | 用 L2（默认）而非 L1 |

`update_color` 与 `update_opacity` **同时关闭**时，脚本直接跳过并说明原因 ——
那种配置下在线更新是空操作，跑它只会白等预算。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| 未观测区域无梯度 | 头顶等被裁掉的部位修不了 |
| 单帧信息量有限 | 用 8 帧左右；帧太多会超预算 |
| 依赖驱动参数质量 | 参数错 → 几何错 → 颜色再怎么调也补不回来 |
| 不修表情/姿态 | 那是 RDF/训练侧的事 |

## 7. 后续可做（不在本次范围）

| 方向 | 说明 |
|---|---|
| **减少默认步数** | 实测 50 步即收敛，`online_update.steps` 可从 300 降到 ~60（约 3.4 s） |
| 回归模型加速 | 用大量热更新结果训练"观测 → 修正量"的回归器，把 10 s 压到 0.1 s |
| 对称先验 | 用左右对称补未观测区域 |
| 与摄像头串联 | RDF → 129 维 → 本模块（需要先解决平移标定） |
