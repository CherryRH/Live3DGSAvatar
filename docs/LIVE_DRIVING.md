# 实时驱动（live）

> 用摄像头（或视频）实时驱动已有模型：RDF 估计 FLAME 参数 → 转成本项目的
> 129 维驱动参数 + 网格 → 渲染推流。

## 1. 为什么必须是独立进程（sidecar）

| | 本项目 | RDF |
|---|---|---|
| Python | 3.10 | **3.11** |
| 关键扩展 | `diff_gaussian_rasterization` | `flame_solver`（**cpython-311 的 .so**） |
| FLAME | 2020 | **2023** |

RDF 的编译产物绑定 CPython ABI，**无法导入 3.10 的进程**。重编一份不是不行，
但会引出"两套 torch / 两个 CUDA 扩展共存"的问题，收益很小。

因此 RDF 作为**独立进程**运行，通过本机 TCP 把结果送过来：

```
realdenseface (py3.11)                 live3dgs (py3.10)
┌────────────────────────┐    TCP     ┌────────────────────────────┐
│ scripts/rdf_bridge.py  │  回环      │ tracking/frame_source.py   │
│  收一帧画面             │ ◀───────── │   取帧（数据集画面）        │
│  infer_image + track   │ ─────────▶ │ tracking/rdf_client.py     │
│  回 x + **顶点**        │  ~59 KB/帧 │   ↓ 只保留最新一帧          │
└────────────────────────┘            │ tracking/live_source.py    │
                                       │  118→129、补牙齿            │
                                       │   ↓                        │
                                       │ Session(live) → core/ → 推流│
                                       └────────────────────────────┘
```

**为什么让 RDF 把顶点也发过来**：这样我们的进程**完全不需要 FLAME2023**，
也就不存在"用 2020 的基去算 2023 的参数"这种错误。顶点 5083×3 float32 ≈ 61 KB，
30 fps 约 1.8 MB/s —— 回环上可忽略。

**为什么是 TCP 而不是 UDP / 管道**

| 方式 | 问题 |
|---|---|
| UDP | 天然 latest-wins，但 62 KB/帧要自己处理分片 |
| 管道（stdout） | 必须由我们 spawn，启动顺序耦合；日志会混进数据流 |
| **TCP 回环** | 启动顺序自由、可 `nc` 调试、断线可重连、改个 IP 就能跨机 |

背压语义在**客户端**实现：取帧线程只把最新一帧交给渲染侧
（与推流的 `asyncio.Queue(maxsize=1)` 同一套）。追踪 15 fps、渲染 45+ fps 时
不会积压，只会复用最新姿态。

## 2. RDF 支持实时吗

**算法层面：支持。** `track_video_online.py` 用 `OnlineGNOptimizer`，跨帧保持
状态（keyframe buffer、用上一帧 `x` 作初值），并自带稳态 FPS 统计。

**接口层面：部分支持。** `VideoInput(source: Path)` 只接受**路径**（视频文件或
图像目录），**没有摄像头索引**。接摄像头需要十几行适配（`cv2.VideoCapture(0)`
循环，直接调 `inferencer.infer_image` + `optimizer.track`）—— 这就是
`rdf_bridge.py` 的职责。

结论：实时能力在算法里，缺的只是"输入源 + 进程间通道"这两层胶水。

## 3. 参数转换

RDF 的 `x`（`dim_x = num_expressions + 18`）：

```
x = [exp 100][global 3][neck 3][jaw 3][eye_l 3][eye_r 3][trans 3]   # 轴角
```

本项目的 `blend_weight`（129）：

```
[0:100] 表情  [100:106] 头姿  [106:112] 下颌
[112:124] 眼球  [124:126] 眼睑  [126:129] 平移
```

三处差异（`tracking/param_map.py` 处理）：

1. **轴角 → rot6d**：取旋转矩阵**前两行**
2. **头姿是复合的**：RDF 把全局旋转拆成 `global` 与 `neck` 两级，
   头姿段填 `R_global @ R_neck`（与其 `_extract_head_rot` 一致）。
   这个假设**必须用真值验证** —— 所以转换函数留了 `compose_head` 开关
3. **眼睑**：RDF 不估计，填 0（数据集的眼睑段也是全 0）

## 4. 坐标对齐（唯一的真正未知）

RDF 与数据集的**相机是同一套**：

| | RDF | 数据集 |
|---|---|---|
| fx | `256/tan(15°)` = **955.4** | `K[0,0]` = 955.4 |
| 相机旋转 | `diag(1,-1,-1)` | `w2v` 的旋转 = `diag(1,-1,-1)` |
| 相机位置 | `(0,0,1)` | 由 `w2v` 推出 `(0,0,1)` |

内参与位姿都相同，**但重建出的头部深度不同**（RDF 的 `camera_distance=1.0`
只是优化初值）。内参固定时，沿相机中心整体缩放**不改变投影** ——
所以差异必然落在"绕相机中心的相似变换"上。

于是按由简到繁的顺序验证（`tracking/align.py`）：

| 模型 | 参数个数 | 含义 |
|---|---|---|
| `fit_scale_about_camera` | **1** | 只是深度估偏了 |
| `fit_similarity` | 7 | 还有旋转/平移分量 |

**先验越少越好**：1 个参数不会被噪声带偏，外推更稳。只有单参数明显不够时才放开。

## 5. 标定流程

真值来自 `render_inputs.npz` 的 `mesh` 与 `blend_weight` —— 它们就是训练管线
实际用的那套，也就是模型"期望看到"的输入。

### 依赖情况

两个环境**不需要额外安装任何东西**：

| 环境 | cv2 | timm | flame_solver | 用途 |
|---|---|---|---|---|
| `realdenseface`（py3.11） | ✓ | ✓ | ✓ | 跑 `rdf_dump.py` / `rdf_bridge.py` |
| `live3dgs`（py3.10） | — | — | — | 跑本项目其余全部脚本 |

**不要在 `live3dgs` 里装 cv2 来"修" RDF 脚本**：`flame_solver` 是
cpython-311 的编译产物，补完 cv2 仍会撞它。先跑环境自检：

```bash
conda activate realdenseface
python scripts/rdf_dump.py --check-deps     # 一行确认环境对不对
```

### 标定

```bash
# ① 导出 RDF 结果（**必须 realdenseface 环境**）
conda activate realdenseface
cd ~/Projects/Live3DGSAvatar
python scripts/rdf_dump.py \
    --images ~/Datasets/INSTA/crh_2/input \
    --out output/rdf/crh_2.npz --limit 300 --no-compile

# ② 标定（live3dgs 环境）
conda activate live3dgs
python scripts/calibrate_rdf.py \
    --rdf output/rdf/crh_2.npz --subject crh_2 --limit 300 \
    --out output/rdf/calibration.json
```

`calibrate_rdf.py` 按顺序回答四个问题（前者不成立时，后者结论不可信）：

1. 表情/下颌/眼球段是否直接对得上？（对不上说明转换层要改，不能靠拟合坐标糊过去）
2. 头姿是 `R_global` 还是 `R_global @ R_neck`？
3. 坐标差是否只是绕相机中心的缩放？
4. 若不是，完整相似变换能做到多好？

## 5b. 标定结果（crh_2，300 帧，已实测）

### 坐标：**不需要变换**

```
单参数（绕相机中心缩放） s=1.001  max=14.5 mm  mean=1.23 mm  p95=3.34 mm
完整相似变换            s=1.002  max=14.2 mm  mean=1.23 mm  p95=3.25 mm
→ 单参数已足够
```

`s ≈ 1.001` 说明 **RDF 的坐标本来就在数据集的空间里** —— 它用深度先验把
尺度定准了，`camera_distance=1.0` 只是个初值。原先"RDF z≈1.0 vs 数据 z≈0.424"
的担心不成立。剩下的 1.2 mm 是重建误差，不是标定残差。

**结论：不做坐标变换**，直接把 RDF 的顶点当世界坐标用。

### 参数：头姿需要复合，表情是"拟合噪声"而非基差异

| 段 | max\|Δ\| | 结论 |
|---|---|---|
| 表情 | 3.29（mean 0.28） | 不是基的差异（见下） |
| 头姿 `R_global @ R_neck` | **0.013** | ✅ 复合假设正确 |
| 头姿 仅 `R_global` | 0.157 | ✗ 差一个数量级 |
| 下颌 | 0.026 | ✅ |
| 眼球 | 0.064 | ✅ |
| 眼睑 | 0 | ✅（两边都补 0）|
| 平移 | 0.0045 | ✅ 直接可用 |

表情段看着差得多，但：

- 逐维相关**中位 0.90、没有一维低于 0.5、也没有一维接近 1.0**
  → 不是置换、不是符号翻转、不是基变换
- **全线性映射（100×100）严重过拟合**：训练 0.033 / 测试 **0.540**（比不修还差）
- 对角缩放只能到 0.240（测试 0.251）
- 误差随帧号下降（0.34 → 0.20）→ RDF 的 identity 在收敛

所以这是**两次不同拟合的分解差异**（RDF 在线跟踪 vs 生成真值的那次拟合），
不是可修正的系统偏差。**不做映射** —— 拟合出来的映射不会泛化。

### 真正要紧的指标：高斯差多少

参数与网格最终都通过模型变成高斯。用 `models/crh_2/test/model.ply` 直接量：

| 差异来源 | 高斯位置差 (mean) | 高斯颜色差 (RGB mean) |
|---|---|---|
| 全部 | 3.76 mm | 0.024 |
| **仅 `blend_weight` 不同** | **0.33 mm** | **0.024** |
| **仅 mesh 不同** | **3.72 mm** | 0.000 |

**参数转换几乎无损**（0.33 mm）；位置差的 99% 来自 mesh ——
也就是 RDF 自身的重建精度，不是我们要标定的东西。
颜色差 2.4% 全部来自表情噪声，量级小但非零。

### 牙齿：需要补，误差约 7 mm

RDF 用原生 FLAME（5023 顶点、9976 面），模型要 5083 顶点、10032 面。
差的 60 个是牙齿顶点，绑着 **1408 个高斯（2.33%）**。

`tracking/mesh_build.py` 用嘴唇圈做刚体锚定补出它们（上牙→上唇圈、
下牙→下唇圈，Kabsch 刚体拟合）。与真值比：

```
mean = 7.2 mm   p95 = 10.4 mm   max = 12.5 mm
```

也试过两种改进，**都没有更好**：

| 方案 | 误差 | 说明 |
|---|---|---|
| 嘴唇 Kabsch（采用） | 7.20 mm | 快，约 1 ms/帧 |
| 含缩放的相似变换 | 7.85 mm | 更差 |
| 反解 5 个关节变换（最小二乘） | 7.48 mm | 更慢（32 ms/帧），无改善 |

说明误差不是"变换估得不好"，而是**我们的模板与 RDF 的 identity 之间的
shape 差异** —— 任何刚体/相似变换都吸收不了。牙齿在口腔内、多数时候被
嘴唇遮挡，这个量级可以接受；但它是一个**已知的、有上界测试守护的**折中。

## 6. 用 crh_2 驱动 crh_1 的模型

这是有意的选择，而不是将就：

| 好处 | 说明 |
|---|---|
| **有真值** | `crh_2/render_inputs.npz` 有 3524 帧的 GT 参数与网格，可以直接量化转换误差 |
| **同管线** | crh_1 与 crh_2 的相机、分辨率、预处理完全一致（`w2v`/`K` 逐位相同） |
| **更接近真实场景** | 用自己的另一段视频驱动模型，正是视频通话的形态（身份来自模型，动作来自输入） |

代价是"驱动者的身份"与"模型的训练对象"不同；但这恰好是**想验证的鲁棒性**，
而不是需要消除的误差 —— 转换误差由 GT 参数衡量，渲染观感单独看。

## 6b. 怎么跑起来

### 两种驱动方式

右侧面板的「驱动」区可以选：

| 方式 | 网格与参数从哪来 | 需要追踪服务吗 |
|---|---|---|
| **数据集（自带参数）** | 所选数据集里已算好的 | 不需要 |
| **RDF 实时追踪** | 追踪服务返回 | 需要 |

「数据集」下拉框列出 `paths.data_root` 下所有可用的数据集（含帧数）。
**切换走 `POST /api/dataset`**（不是 WS 的 params）：它要重载 scene，慢且可能失败，
前端会显示全页加载浮窗，成功后回到第 0 帧并暂停，失败则不动状态并回滚下拉框。
**换数据集会自动重载**：相机、帧号上限、送追踪服务的画面都跟着换。

### 数据集能随便换吗

**能，只要拓扑一致。** 校验对象是**模型自带的数据集**（顶点数 + 面数），
不是别的。当前三个数据集都是同一套 FLAME + 牙齿（5083 顶点 / 10032 面），
所以 `crh_1` 的模型可以直接用 `crh_2` 或 `duda` 的数据驱动 —— 这正是
`docs/ONLINE_UPDATE.md` 里那些跨数据集实验在做的事。

拓扑不一致时会**明确报错**（报出两边的顶点数/面数），而不是画出错位的图。

### 送哪个目录的画面给追踪服务

| 目录 | 内容 | 优先级 |
|---|---|---|
| `input/` | 视频裁出的**原始画面**（自然背景）| 首选：与真摄像头同一分布，已实测可追踪 |
| `images/` | **已抠图**的人像（黑底 + alpha）| 回退：有些数据集（如 `duda`）只有这一份 |

默认 `auto`，可用 `tracking.frame_subdir`（`auto` / `input` / `images`）强制指定。
界面会显示实际送的是哪个目录（`RDF 15 FPS · 送 input/`）。

> `images/` 是黑底、边缘带 alpha 过渡，与追踪器训练时的自然图像分布不同 ——
> 人脸检测仍能工作，但属于**未实测**的输入，所以默认不优先选它。

### 追踪服务是通用的

`scripts/rdf_bridge.py` 现在是一个**无状态的"画面进、参数出"服务**：

```
客户端 ──一帧 RGB──► 追踪服务 ──参数 + 网格──► 客户端
```

它不关心画面从哪来（数据集回放、摄像头、单张图片都可以），所以：

```bash
# 终端 A：追踪服务（realdenseface 环境）
conda activate realdenseface
cd ~/Projects/Live3DGSAvatar
python scripts/rdf_bridge.py --port 8980

# 终端 B：本项目（live3dgs 环境）
conda activate live3dgs
bash run_gui.sh
```

启动时它会预构建一次（默认 512×512，`--width/--height` 可改）。
客户端送来的尺寸不同会自动重建相机 —— 所以同一个服务能同时应付
数据集（512²）和摄像头（如 640×480）。

面板里选「RDF 实时追踪」，取帧线程就会把所选数据集的 `input/` 一帧帧发过去。

### 拿不到观测时会发生什么

**回退到所选数据集的首帧**，而不是黑屏或报错：

| 状态 | 画面 | 界面提示 |
|---|---|---|
| 追踪服务未启动 | 数据集首帧 | `⚠ 显示首帧（未连接 RDF 桥接进程…）` |
| 已连接但无响应 | 数据集首帧 | `⚠ 显示首帧（已连接，但 1.0s 内没有新帧）` |
| 数据集缺 `input/` | 数据集首帧 | `⚠ 显示首帧（数据集没有 input/ 目录…）` |
| 正常 | 追踪结果 | `RDF 15 FPS · 帧间隔 0.03s` |

**回退必须可见**：不说明的话，用户会以为实时驱动在工作。

### 为什么渲染帧率会掉到追踪帧率

追踪约 15 fps、渲染能到 45 fps 以上。照常按帧数上限渲染会把**同一份内容渲染 3 次**，
白白占用 GPU —— 而 GPU 正是追踪的瓶颈，等于自己拖慢自己。

所以 live 模式下"**没有新观测就不重渲**"：帧率会诚实地掉到内容更新率。
数据集模式**保持原语义**（"暂停 ≠ 停止渲染"，链路始终是活的）——
两者行为不同是刻意的。

### 播放 / 暂停 / 跳帧：两种模式一致

播放条在两种驱动方式下都有效：

| 操作 | 数据集模式 | RDF 模式 |
|---|---|---|
| 播放 | 渲染循环推进帧号（渲染一帧 = 播放一帧）| 取帧线程推进（**追踪一帧 = 播放一帧**）|
| 暂停 | 帧号停住，仍按帧数上限重渲同一帧 | 帧号停住，**重送同一帧**给追踪服务 |
| 跳帧/单步 | 立即取该帧 | 立即送该帧给追踪服务 |

RDF 模式的播放速度因此等于追踪速度（约 15 帧/秒），而不是渲染帧率 ——
画面内容只随追踪结果变化，按渲染帧率推进会让播放条与内容脱节。

暂停时不会满负荷重送：观测有 `max_age` 过期判定，停了就会"看不见"，
所以按**过半衰期才重送一次**（约 2 次/秒）保持新鲜。序号用帧号，因此
重送同一帧不会触发重渲。

| | 数据集（自带参数） | RDF 实时追踪 |
|---|---|---|
| 网格 | 数据集现成的（含 60 个牙齿） | RDF 的 5023 顶点 + 本地补牙齿 |
| 参数 | 数据集现成的 129 维 | RDF 的 118 维 → 转换 |
| 调试扰动 | 有效 | 无意义（后端忽略）|
| 追踪线程 | 不启动 | 启动 |

**数据集模式下不启动追踪线程**：RDF 推理与渲染抢同一块 GPU，
没人用的时候没必要让它空转。

## 6c. 线上格式

请求（客户端 → 服务）：`RDFQ | seq | w | h | rgb[w*h*3]`，一帧约 0.9 MB（640×480）。
回复（服务 → 客户端）：约 59 KB，30 fps 约 1.8 MB/s，回环可忽略。

```
请求  RDFQ | seq I | width H | height H | rgb (RGB888)
回复  RDFF | seq I | timestamp d | n_verts H | n_exp H | x[118] | verts[5023*3]
```

两个设计要点：

- **没有握手**：回复头自带 `n_verts` / `n_exp`，客户端不必预先知道 RDF 的配置
- **顶点由服务侧算**：本端因此不需要 FLAME2023，也就不会出现
  "用 2020 的基算 2023 的参数"

读端必须**循环读满**（`recv` 返回片段是常态）。这一条有集成测试守着：
测试里的假服务故意把回复切成 4 KB 片段发送。

## 7. 分层与边界

```
tracking/param_map.py   纯函数：118 → 129
tracking/align.py       纯函数：相似变换拟合/应用
tracking/mesh_build.py  补 60 个牙齿顶点（5023 → 5083）
tracking/rdf_wire.py    纯函数：请求/回复的编解码（自描述）
tracking/rdf_client.py  网络：一问一答，断线自动重连
tracking/frame_source.py 取帧：数据集 input/ 优先，images/ 回退
tracking/live_source.py 组装：取帧线程 → 追踪 → (mesh, blend_weight)
scripts/rdf_dump.py     离线导出（realdenseface 环境）
scripts/rdf_bridge.py   追踪服务（realdenseface 环境）
```

`tracking/` 可以依赖 `core/types`，但**不得**被 `core/` 导入 ——
驱动来源（数据集 / 摄像头 / 桥接进程）是可替换的外部依赖。
